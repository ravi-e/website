After a decade of managing documentation in large enterprise setups using traditional help authoring tools like **MadCap Flare** and **DITA XML**, I realized that the developer-first ecosystem requires a different approach. Tech-centric companies are shifting toward **Docs-as-Code**. 

This shift is not just a change of formatting languages from XML to Markdown; it is an organizational alignment. It means treating technical communication with the same engineering rigor as the code itself.

## Why Docs-as-Code?

The benefits of the Docs-as-Code methodology are clear:

1. **Version Control Integration:** Merging content changes through git branches and pull requests prevents overwritten files and offers perfect revision history.
2. **Developer Alignment:** Engineers are much more likely to contribute to documentation if they can make edits directly in their IDEs rather than logging into external portals.
3. **Automated Validation:** CI/CD pipelines can run linters, link-checkers, and build tests before publishing, raising the overall bar for documentation quality.

## My Current Career Strategy

To transition my enterprise skillset to this modern developer ecosystem, I am focusing on three key initiatives:

* **Building a Live Sandbox:** Instead of displaying static PDF portfolios, I built this website using **Eleventy (11ty)**, hosting it on GitHub and managing changes via git branches. This serves as a working demonstration of version control, markdown structures, and site compilation.
* **Demonstrating Multi-Format Competency:** Showing that I can handle CLI syntaxes, REST API JSON models, and diagnostic tables just as comfortably as deep concept articles.
* **Open Collaboration:** Publishing code samples and documentation templates publicly to invite feedback and show process transparency.

> "Great documentation isn't built in a silo. It is co-authored by writers, engineers, and the feedback loop of its readers."
